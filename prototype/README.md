# 校园垃圾分类投放引导助手

AI+场景创新赛道参赛原型。

切口：**不做"这是什么垃圾"的识别，只解决复合垃圾怎么拆、怎么投。**
聚焦四类校园投放点：宿舍楼 / 教学楼 / 食堂 / 快递点。

> ⚠️ 仓库内的规则取值、知识库、识别场景**均为演示数据**。
> 提交参赛材料前必须替换为真实调研与真实照片，并核实所有分类目录条文。
> 同时检查所有材料中**不得出现学校名称、Logo 与指导教师信息**。

## 一、先说风险：这个选题的创新性在哪里

垃圾分类拍照识别是**老题目**。支付宝、微信小程序、各地政务 App 都做过，
如果作品只是"拍照 → 告诉你属于哪一类"，评审判为"常规应用"的概率很高
（创新性只能拿 0-6 分档）。

所以本原型把切口收窄到了**现有产品普遍做不好的那一环**：

| 现有产品怎么做 | 本作品怎么做 |
| --- | --- |
| 识别单一物品，回答"属于哪一类" | 识别**复合物品的多个部件**，回答"拆成几部分、每部分投哪" |
| 给单一结论："餐盒属于可回收物" | 给**条件化结论**："洗净投可回收，洗不净投其他垃圾" |
| 不管投放前的动作 | 明确"倒空 / 冲洗 / 沥干 / 撕碎"四类前置动作 |
| 不区分地区 | **地区标签可切换**（上海显示"湿垃圾/干垃圾"，北京显示"厨余/其他"） |

**核心论证**：真正的痛点不是"不知道塑料可回收"，而是"不知道脏的塑料餐盒不能回收"。
**类别判定常常是有条件的**，而现有工具都在给无条件答案。这就是本作品的技术切入点。

## 二、怎么打开（三种方式）

### 方式一：双击启动（推荐）

直接双击 `启动原型.cmd`。脚本会自动检查环境、启动服务，
并**自动用默认浏览器打开页面**，不需要记任何命令。

关闭那个命令行窗口即可停止服务。

### 方式二：公网访问（手机用流量也能打开）

双击 **`公网访问.cmd`**。它会启动本机服务，并通过 Cloudflare 隧道
生成一个公网地址，**手机无论连 WiFi 还是用移动数据都能打开**。

首次运行会自动下载隧道工具（约 53 MB），之后直接复用。

```
  公网地址： https://xxxx-xxxx-xxxx.trycloudflare.com
  二维码：   data/exports/公网访问二维码.png   （用手机相机扫）
```

注意：

- 公网地址**每次启动都会变**，以控制台输出的为准；
- 这个地址任何人都能访问，等于把模型额度开放出去了，
  不想公开时按 `Ctrl+C` 关闭，或改用方式一；
- 想加访问密码：在 `.env` 里填 `GRADIO_AUTH_USER` 与 `GRADIO_AUTH_PASSWORD` 即可。

### 方式三：命令行

```powershell
cd prototype
powershell -ExecutionPolicy Bypass -File run.ps1
```

浏览器打开 `http://127.0.0.1:7860`。

### 同一 WiFi 下的手机访问

如果手机和电脑连同一个 WiFi，不需要公网隧道，直接用局域网地址即可：

```powershell
.\.venv\Scripts\python.exe scripts\lan_access.py
```

它会打印局域网地址、生成二维码，并列出打不开时的排查清单
（最常见的是 Windows 防火墙未放行，以及公共 WiFi 的客户端隔离）。

### 打不开怎么办

> **打不开怎么办？**
> 1. 先跑一次 `python scripts\diagnose_ui.py`，它会构建界面并报告所有警告；
> 2. 如果 7860 端口被别的程序占用，程序会**自动顺延到 7861、7862…**，
>    并在控制台打印实际地址，请以控制台输出的地址为准；
> 3. 命令行窗口如果已经关闭，服务也同时停止了——重新双击 `启动原型.cmd` 即可。

```powershell
.\.venv\Scripts\python.exe scripts\smoke_test.py
.\.venv\Scripts\python.exe eval\run_waste_eval.py
```

## 三、核心功能：拍照识别 → 拆解引导

### 界面设计：Organic 锚点（frontend-design 技能）

界面按 `frontend-design` 技能的 **Organic（有机）** 锚点设计，全部 token 严格取自锚点定义。

**为什么选 Organic，而不是安全的"干净工具风"**：
垃圾分类的物理终点是自然循环——厨余回到土壤，可回收物回到生产线。
Organic 的大地色系直接对应这条物质链。而把它用在一个高密度、要快速决策的
分拣工具上，是一种有意为之的张力：用最"慢"的视觉语言，承载最"急"的操作场景。

刻意避开两件俗套：**不用绿色**（几乎所有环保产品都用环保绿，这个符号已失效）；
**不用奶油白**（锚点明确禁止 #F0-F8 暖纸色区间）。

| Token | 落地 |
| --- | --- |
| 表面 | 页面底=深苔 `#3A4032`，内容面=沙 `#E8DCC7`，次级面=燕麦 `#D4B895` |
| 字体 | 人文衬线：Fraunces（锚点限定显示字体）+ 本机 Noto Serif SC，**全站无无衬线** |
| 结构 | 圆角 16–32px，全站不出现直角矩形 |
| 质感 | SVG `feTurbulence` 颗粒，2–3% 不透明度 |
| 动效 | 320 / 360 / 420ms 缓动；首屏苔绿弧带 7.5s 呼吸；尊重 `prefers-reduced-motion` |

**四分类映射到大地色**（颜色承担信息功能）：

| 类别 | 色名 | 色值 |
| --- | --- | --- |
| 可回收物 | 赭石 ochre | `#C08E3A` |
| 有害垃圾 | 赤陶 terracotta | `#C66B3D` |
| 厨余垃圾 | 苔绿 moss | `#606C38` |
| 其他垃圾 | 陶土 clay | `#B08B6E` |
| 液体 | 鼠尾草 sage | `#8B9D83` |

### 签名动作：地层条（Strata Bar）

每个识别结果顶部有一条按类别数量比例分割的**有机曲线带**，像一段土壤剖面：
段宽严格等于该类别在本次结果中的占比，段与段之间是不对称圆角形成的手绘感边界，
切换照片时以 420ms 缓动重新分配宽度。

它是「分类构成」的可视化，也是这个页面的签名——面对一张有 20 件物品的混投照片，
用户不必读数字就知道"可回收占了大头"。

### 内容纪律

按技能 §2 执行：屏幕上每个字符串都是真实信息（识别出的部件、规则库给出的类别、
真实计数与耗时）；**不使用 Unicode 符号充当图标**（类别标记是手写的内联 SVG 矢量图标）；
标准操作使用标准文案；不出现无人索要的装饰性小标题。

### 保真度自检

```powershell
.\.venv\Scripts\python.exe scripts\check_anchor_fidelity.py
```

机械化检查 21 项：无纯白/纯黑/冷灰/奶油白、无直角矩形、锚点色板命中 7/7、
含 feTurbulence 颗粒且透明度在 1–3%、存在 300–500ms 缓动、有首屏呼吸动效、
全站仅衬线字体、地层条已渲染、无 Unicode 图标、标准文案未被替换。

渲染逻辑集中在 `app/render.py`（设计令牌 + HTML 生成），
Gradio 自身的按钮、标签页、输入框也通过主题与 CSS 一并改造。

### 作品介绍页（独立落地页）

`../landing/` 是一份独立的作品介绍页，给评委看的，与工具本身分开。

**它和原型共用同一个服务**：原型在站点根，作品页挂在 `/landing/`。
共用一个端口意味着内网穿透只需要一条隧道，对外只分享一个地址：

```
http://127.0.0.1:7860/          原型
http://127.0.0.1:7860/landing/  作品介绍页
```

公网访问时同理，在隧道地址后加 `/landing/` 即可。
作品页里指向原型的按钮用相对路径 `/`，因此隧道地址每次变化都不会失效。

预览方式：双击 `预览作品页.cmd`（会自动确认服务状态并打开页面），
或者直接在原型界面的**首屏**点「作品介绍页」按钮。

入口有三处，互为备份：

| 入口 | 位置 | 说明 |
| --- | --- | --- |
| 首屏按钮「安装到手机」 | 页面最上方 | 能装就直接弹安装框，装不了就跳到 `/app` 说明原因 |
| 首屏按钮「作品介绍页」 | 页面最上方，不用切页签 | 主入口，44px 可点高度 |
| 首屏按钮「扫码分享」 | 页面最上方 | 跳到 `/share`，二维码始终指向当前地址 |
| `⑤ 方案素材` 页签内的按钮 | 页签里 | 答辩时按流程走的入口 |
| 短地址 `/app` | 地址栏 | 安装引导页，分情况判断能不能装、怎么装 |
| 短地址 `/info` | 地址栏 | `/landing/` 的别名，口播和手输更短 |

**所有入口都必须是按钮，不能用 Markdown 行内链接**：行内链接渲染出来框高只有 20px，
低于 44px 的可点尺寸，手机上点不准。`gr.HTML(render.cta_html(...))` 负责生成这类按钮。

### 展示海报（Photoshop）

`scripts/build_poster.jsx` 用 Photoshop 脚本排一张竖版长海报，
结构照着常见的设计类作品海报来：顶部通栏 → 主视觉 → 编号模块 → 底部通栏。

```powershell
# 1. 先把网页截成图（只截图，不改页面、不改地址）
node scripts\poster_shots.mjs

# 2. 再用 Photoshop 排版，产出分层 PSD 与 PNG
#    路径走 ASCII 临时目录，ExtendScript 处理中文路径不稳
$app = New-Object -ComObject Photoshop.Application
$app.DoJavaScript("$.evalFile('.../build_poster.jsx')")
```

产物在 `data/exports/poster/`：

| 文件 | 说明 |
| --- | --- |
| `poster.psd` | 47 个图层，截图、色块、文字各自独立，可直接改 |
| `poster.png` / `poster.jpg` | 1080 × 6519，用于预览和提交 |
| `10-…` ~ `53-…` | 20 张中间截图，2 倍 / 3 倍分辨率 |

两个容易踩的坑，已经写进脚本注释：

1. **`layer.bounds` 返回的是带单位的字符串**（`"0 px"`），拿它直接做减法会被
   UnitValue 的隐式转换带偏，实测把 `(60, 1106)` 算成 `(-60, -1106)`，
   截图整块跑到画布外、导出的图上只剩底色。必须 `parseFloat` 后再算，
   移动后回读坐标自校验。
2. **截图必须统一色模式**。Playwright 默认浅色，原型页会渲染成燕麦底，
   与 `/app`、`/share` 的深苔底对不上。全部用 `colorScheme: 'dark'` 截图，
   图片才能直接落在版面上、不出现色块接缝。

它按 `design-taste-frontend`（taste-skill）的协议构建：

| 步骤 | 结论 |
| --- | --- |
| Design Read | competition-entry project page for expert judges, trust-first evidence-led language |
| 三个旋钮 | `DESIGN_VARIANCE 6` / `MOTION_INTENSITY 4` / `VISUAL_DENSITY 4`（由 design read 推导，非基线默认）|
| 设计系统 | 不属于 §2.A 的任何官方系统，按 §2.B 如实标注为审美方向，用原生 CSS |
| 字体 | Outfit，**自托管**（技能禁止用 `<link>` 引 Google Fonts）|
| 配色 | 单一强调色（深苔绿），浅深两套由 `prefers-color-scheme` 驱动 |
| 图片 | 使用项目自采的 4 张真实校园照片，无假截图、无图标库依赖 |
| 图标 | 一个都不用（技能允许 "or use nothing"，也避免 CDN 依赖）|

### 可读性审计（对比度）

```powershell
.\.venv\Scripts\python.exe scripts\check_contrast.py
```

把 CSS 里声明的文字色与它实际落到的背景配对，按 WCAG 算对比度，逐项报出不合格项。

**这一轮抓到的最大问题**：为了让自定义沙面面板生效，早期把所有 Gradio 容器
设成了透明。结果是**原生组件的深色文字直接落在深苔色页面底上，对比度只有 1.33:1**，
几乎不可见。受影响的包括：

| 组件 | 修复前 | 修复后 |
| --- | --- | --- |
| 页面底上的正文（继承 body 颜色） | 1.33:1 | 6.39:1 |
| gr.Dataframe 表格单元格 | 1.33:1 | 10.55:1 |
| gr.Markdown 正文 | 1.33:1 | 10.55:1 |
| gr.Files 文件列表 | 1.33:1 | 10.55:1 |
| gr.Code 代码块 | 1.33:1 | 10.55:1 |
| gr.Chatbot 对话气泡 | 1.33:1 | 10.55:1 |
| 三级文字（--ink-3） | 3.95:1 | 4.73:1 |
| 浅色模式标签页按钮 | 4.16:1 | 5.36:1 |

修法是给每个原生组件补上沙面与墨色声明，并把页面级的默认文字色
从"墨色"改成"页面级浅色"（新增 `--on-page` 令牌）。
现在**深浅两套模式、18 组文字/背景配对全部达到 WCAG AA**。

### 移动端布局审计

```powershell
node scripts\mobile_audit.mjs     # 三个手机视口实测：溢出、字号、点击区域
node scripts\mobile_chain.mjs     # 出现横向溢出时，定位是哪一层撑宽的
```

用 Playwright 驱动系统自带的 Edge 无头渲染，在 375 / 390 / 412 三种手机宽度下逐元素测量。

**这一轮抓到的最大问题**：手机视口 390px，页面被撑到 **782px**，
横向滚动条超过一屏两倍。原因是 `.gradio-container` 作为 flex 子项
只写了 `max-width` 而没有 `width` 与 `min-width: 0`，不会收缩到视口宽度。

同时发现的另外三个问题：

| 问题 | 原因 | 修法 |
| --- | --- | --- |
| 6 个标签页横排溢出视口，只能看到前三个 | 标签栏不换行 | 允许换行 + 缩短标签文案 + 抬到 44px 可点高度 |
| 部件行中间文字被挤成窄缝 | 右侧类别胶囊占位 | 手机上胶囊独占一行置顶 |
| 下拉框内部输入框只有 22px 高 | 未覆盖 Gradio 内部控件 | 统一抬到 44px |

**还有一个更隐蔽的根因**：Gradio 会重写通过 `gr.Blocks(css=...)` 传入的选择器，
例如

```
我的：.gradio-container .tabs .tab-container:not(.visually-hidden) button
实际：.gradio-container.gradio-container-5-50-0-dev0 .contain .gradio-container .tabs ...
```

其中 `.contain .gradio-container` 这一层在真实 DOM 里并不存在，规则因而失效。
一部分规则侥幸保留了未加前缀的副本所以看起来正常，带 `:not()` 的则完全失效。
**改为把样式直接注入 `<head>`**，绕开这个改写，样式才真正可预期。

最终结果：**原型与作品页在三种手机宽度下全部通过**，
桌面端（1440 / 1920）无横向溢出回归。

### 安装成手机 App（PWA）

项目已经做成 **PWA（可安装的网页应用）**。在手机上打开公网地址后，
浏览器菜单里选「添加到主屏幕」，就会得到一个有独立图标、
全屏运行、没有浏览器地址栏的应用。

**装的时候直接打开 `/app`**，那一页会把当前情况判断清楚，不用自己猜：

| 情况 | 页面会怎么提示 |
| --- | --- |
| 安卓 Chrome / Edge | 出现「安装到手机」按钮，一点就弹系统安装框 |
| iPhone / iPad | 给出 Safari 分享 → 添加到主屏幕 的三步 |
| 在微信里打开 | 提示先「在浏览器打开」，微信内置浏览器装不了 |
| 用的是局域网或本机地址 | 提示安装要求 https，让改用公网地址 |
| 已经装好了 | 显示"已安装"，不再劝你装 |

原型首屏也有「安装到手机」按钮：浏览器肯给安装事件时**直接弹系统安装框**，
拿不到事件时才跳到 `/app` 看分步说明。

不需要应用商店、不需要签名，也不需要任何构建工具链。

**为什么不做原生 APK**：识别功能要把照片发到云端视觉模型，
必须联网才能工作。原生 App 一样要连服务器，只是多了一层打包；
而 PWA 能直接用，还能在答辩现场扫码安装给评委看。

> **PWA 与 APK 的真实差别**：PWA 装出来同样有桌面图标、独立窗口、独立任务栏条目，
> 安卓上由 Chrome 编译成 WebAPK，系统里就是一个应用。
> 它和 APK 的区别是：APK 能离线带界面、能调原生能力；

### 第一步：视觉识别（`app/vision.py`）

把照片变成**部件清单**，不判断类别。复合物品必须拆成部件逐一列出：

```json
{"summary": "一杯未喝完的珍珠奶茶",
 "items": [{"name": "奶茶杯身", "material": "PP塑料", "confidence": 0.94},
           {"name": "塑料杯盖", "material": "PP塑料", "confidence": 0.89},
           {"name": "剩余液体", "material": "液体", "confidence": 0.92}]}
```

**为什么识别层不判类别**：类别归属高度依赖地区标准与现场条件（洗干净没有），
属于确定性问题，交给规则库比交给模型可靠得多。

### 第二步：拆解与引导（`app/disassembler.py`）

匹配复合规则 → 展开每个部件 → 输出分步指令。实际输出示例：

```markdown
### 这是复合垃圾：没吃完的外卖餐盒
**需要拆成 4 部分分别投放**

| 部件 | 投放类别 | 投之前要做 |
| --- | --- | --- |
| 剩饭剩菜与汤汁 | 湿垃圾（绿色桶） | 汤汁倒入水槽；固体食物倒入厨余垃圾桶 |
```

## 四、规则库（`rules/waste_sorting.yaml`）

| 组成 | 数量 | 说明 |
| --- | --- | --- |
| 复合垃圾规则 | 8 类 | 奶茶、外卖餐盒、快递纸箱、泡面桶、咖啡杯、中性笔、口罩湿巾、充电器数据线 |
| 单一物品规则 | 56 类 | 通用易错单品 + 校园专属 + 投放点混投物品 + 大件与废品 |
| 地区标准 | 4 套 | national / beijing / shanghai / guangzhou |

每条规则包含：部件拆分、投放类别、**投放前处理动作**、**条件化说明**、
**常见误投点**、地区差异提示。教师与环卫人员可直接增删，**不需要改代码**。

### 两个容易踩的坑（已处理）

1. **地区标签残留**：规则文本里写死了"其他垃圾"，切到上海口径时会前后矛盾。
   引擎会统一本地化，并把桶名简写（"厨余桶" → "湿垃圾桶"）一并处理。
   这个问题有专门的回归测试（见评测的"地区标签一致性"）。
2. **规则覆盖漏洞**：识别出的是"充电头"，规则里写的是"充电器"，导致匹配失败。
   评测会直接暴露这类问题（w08 曾经出现过）。

### 真实照片暴露的另外三个质量问题（已修）

用真实照片跑第一遍时，除了覆盖率低，还暴露出：

1. **重复条目**：一张照片里有 4 个易拉罐，输出就列 4 行一样的表格。
   现在按规则合并为一条并标注数量（`金属易拉罐 ×4`）。
2. **复合规则误匹配**：一袋混合垃圾因为偶然出现"餐盒""塑料袋"两个词，
   被判定成"没吃完的外卖餐盒"。
   现在**照片里的物品越多，认定复合垃圾所需的触发词越多**
   （≥8 件要求 +1，≥15 件再 +1），避免堆量大时误判。
3. **分拣优先级里有硬编码类别名**：切到上海口径后输出仍是"其他垃圾"，
   前后矛盾。**地区标签一致性回归测试直接抓到了这个 bug**（一度掉到 0.4444）。

第 3 条很能说明回归测试的价值——这个 bug 是人眼看一遍很难发现的。

### 新增：混投检查（拍投放点桶时用）

真实照片里有一张是**装满塑料、纸板、金属罐、木框的绿色厨余桶**——整桶都是混投。
系统如果只逐件回答"这个投哪"，答不了「这个桶里的东西放对了吗」这个更实际的问题。

所以在界面上加了「这是哪个桶」选择器，选定后自动列出不该出现在该桶里的物品：

```
🚫 混投检查：这个桶是「厨余垃圾桶」桶，以下 6 项不该投在这里
- 塑料袋 ×2 应投可回收物（蓝色桶）
- 纸板与瓦楞纸 应投可回收物（蓝色桶）
- 金属易拉罐 应投可回收物（蓝色桶）
- 木材与木制品 应投其他垃圾（灰色桶）
- 复合包装袋（铝箔复合膜） 应投其他垃圾（灰色桶）
```

实测：该照片 **6/6 项均为混投**；另一张蓝色可回收桶照片 **0/3 项混投**（投放正确）。

命令行等价用法：

```powershell
.\.venv\Scripts\python.exe scripts\check_bin.py --photo _89_ --bin kitchen
```

### 新增：分拣优先级

面对"一堆混在一起的垃圾"（投放点照片的典型形态），逐个念表格不好用。
部件数 ≥ 4 时会额外给出处理顺序：

```
1. 必须单独挑出：药品泡罩包装（→ 有害垃圾）—— 混进别的桶会造成污染与安全风险
2. 先分离出来：食物残渣、剩饭剩菜、果皮果核 ×2（→ 厨余垃圾）
3. 再冲洗沥干：塑料餐盒 ×2、金属易拉罐 ×4、瓶盖…（→ 可回收物）
4. 最后投放：一次性纸杯、塑料托盘（→ 其他垃圾）
```

### 校园版的差异化设计：投放点桶位差异

校园与居民小区最大的不同：**同一件垃圾，在不同投放点可能要投不同的桶**，
因为各投放点的桶位配置并不一致。

| 投放点 | 可回收物 | 厨余垃圾 | 有害垃圾 | 其他垃圾 | 常见问题 |
| --- | --- | --- | --- | --- | --- |
| 宿舍楼 | ✅ | ⚠️ 部分楼栋无 | ⚠️ 集中回收点 | ✅ | 厨余无处可投，只能混进其他垃圾 |
| 教学楼 | ✅ | ❌ | ⚠️ 部分楼层 | ✅ | 奶茶杯、纸巾、草稿纸混投最严重 |
| 食堂 | ✅ | ✅ | ❌ | ✅ | 剩饭剩菜与一次性餐具混投 |
| 快递点 | ✅ | ❌ | ❌ | ✅ | 拆箱高峰纸箱堆积，胶带面单未分离 |

系统提示词会要求助手在给出引导时**提醒用户确认现场桶位**，
而不是想当然地说"投厨余桶"。详见 `knowledge/waste_sorting/05_校园投放点差异说明.md`。

校园还有明显的时间规律：开学季是快递纸箱高峰、考试周是草稿纸与奶茶杯高峰、
夏季饮料瓶最多、冬季外卖泡面比例上升——知识库里按这四个时段给了引导重点。

### 调试过程中修掉的两个真问题

**1. 通用疑问词污染打分。**「今天下午有没有篮球赛？」曾拿到 **0.2488** 分而被误答——
文档里"有没有"出现了 3 次，"有没"这个二元组把分数抬了上去。
扩充停用词表后降到 **0.0000**。

**2. 含领域词但知识库答不了的问题。**「学校附近哪家奶茶店好喝？」
「垃圾分类这个政策是哪一年开始的？」含领域词，词法上无法与真问题区分。
解决办法是**由场景作者声明非知识型意图**（`out_of_scope_patterns`），
对推荐类、评价类、时效类问法直接拦截。

> 这个方案是词法层面的工程折中：它覆盖已知问法模式，新问法需要人工补充。
> 更彻底的做法是把 `RELEVANCE_GATE` 设为 `llm`，用模型做二次意图判定。
