# 选题论证（喂给方案书的「项目概述」与「需求分析」）

> 本文档是**选题决策的论证稿**。所有带 ⚠️ 的数字必须替换为你自己的真实调研数据
> （问卷、访谈、投放点统计），否则会被评审判定为"数据不实"。

## 一、选题的两条硬约束

1. **小切口、体系化**：不写宏大的"智慧校园/智慧社区"，只聚焦一类具体难题，
   并形成能长期运行的模式。
2. **痛点真实可量化**：必须是长期存在的问题，且有可采集的数据支撑。

## 二、先承认风险：垃圾分类识别是老题目

支付宝、微信小程序、各地政务 App 都已经提供"拍照识别垃圾类别"功能。
如果作品只做到"拍照 → 告诉你属于哪一类"，会被评委归入**常规应用**
（评分表创新性项只有 0-6 分档）。

所以选题的关键不是"做不做垃圾分类"，而是**在垃圾分类里切哪一刀**。

## 三、切口对比

| 候选切口 | 小切口程度 | 体系化闭环 | 痛点可量化 | 数据可得 | 判定 |
| --- | --- | --- | --- | --- | --- |
| A 全类别拍照识别（识别所有垃圾属哪一类） | 宽 | 弱：只是查询工具 | 高 | 中：需大量标注图片 | **淘汰**：已有大量成熟产品，创新性存疑 |
| B **复合垃圾拆解式投放引导** | 极窄：只做复合物品 | 强：识别→拆解→引导→误投沉淀→规则更新 | 高 | 高：可自采照片、可拿投放点数据 | **选用** |
| C 投放点误投数据看板 | 中 | 中 | 高 | 中：需投放点配合 | 作为 B 的闭环延伸，不单独成题 |
| D 志愿者值守替代 | 宽 | 弱 | 中 | 高 | 淘汰：本质是 B 的应用形态 |

## 四、为什么选 B

### 1. 现有产品的真实缺口不是"识别不准"，而是"不告诉你怎么做"

现有工具的回答形态是：**"某物属于 X 类"**。

但真实投放场景里的问题长这样：

- 一杯没喝完的奶茶 —— 它不是"一件垃圾"，而是**液体 + 杯身 + 杯盖 + 吸管**四件；
- 一份没吃完的外卖 —— 餐盒**是否冲洗干净**，决定它投可回收还是其他垃圾；
- 一个快递纸箱 —— 纸箱可回收，但**胶带、面单、气泡膜都不可回收**。

**结论：类别判定常常是有条件的，而现有工具都在给无条件答案。**
这就是本作品的切入点。

### 2. 这个切口可以被程序精确处理

- **拆解**：复合物品 → 部件清单，是确定性的结构化展开；
- **条件判定**：把"是否洗净""是否干燥"作为条件分支写进规则，不需要模型猜；
- **地区差异**：类别名称与部分归属随城市变化，做成可切换的标签体系；
- **前置动作**：倒空 / 冲洗 / 沥干 / 撕碎，是固定四类动作。

这些都可以用规则库精确表达，**不需要依赖模型的自由发挥**，
因此结果可复现、可审计、可被使用者自行维护。

### 3. 痛点可被精确量化

| 指标 | 采集方式 |
| --- | --- |
| 复合垃圾误投率 | 投放点抽样统计（按物品类型分类计数） |
| 现有工具引导可执行率 | 人工评测：随机取 50 件复合垃圾，看现有工具能否给出可执行步骤 |
| 本系统引导覆盖率 | 规则库能覆盖的部件数 / 实际出现的部件数 |
| 条件化判定命中率 | 评测集上类别判定正确的比例 |
| 保洁二次分拣工作量 | 保洁人员访谈 + 分拣耗时记录 |
| 志愿者值守工时 | 值守排班表统计 |

⚠️ **待你补真实数据**：本校投放点的实际误投率、志愿者值守工时、
保洁二次分拣耗时。这些需要实地统计与访谈，是本作品"需求分析"得分的关键。

### 4. 能形成长期运行的模式

```
学生拍照 → 获得拆解引导 → 正确投放
                ↓
        误投记录归集（按投放点、按物品类型）
                ↓
        规则库 / 知识库更新（每学期一次）
                ↓
        下一轮识别更准、引导更全
```

关键是**每年沉淀**：把投放点新出现的误投类型补进规则库，
系统能力随使用时间增长，而不是一次性交付后废弃。
这直接对应评分表的"项目实施"与"应用效果"。

## 五、技术选型为什么这样定

| 环节 | 交给谁 | 理由 |
| --- | --- | --- |
| 画面 → 部件清单 | 多模态大模型 | 需要理解"这是一杯没喝完的奶茶"这种场景语义，规则做不到 |
| 部件 → 投放类别 | 规则库 | 类别归属依赖地区标准与条件分支，必须精确、可审计 |
| 依据解答 | RAG 检索 | 分类总则与地区差异需要可溯源 |
| 分步指令生成 | 规则库 + 模板 | 指令必须稳定一致，不能让模型每次说得不一样 |

**核心主张：不是"用大模型做一切"，而是让感知任务与判定任务各归其位。**
答辩被问到"模型识别错了怎么办"时，这是有力回答：
识别错了只影响部件清单，类别判定不会跟着错——因为判定不依赖模型。
